JailbreakFirewall

Runtime guardrails

A web application firewall for LLM inputs: classify and block jailbreaks and prompt injections before they reach the model.

startups/01-jailbreakfirewall/
95.8%
held-out accuracy on a 383-example split (96 test)
1.000
precision on the held-out split
11/11
demo prompts matched their expected label
0.80
risk on a base64-obfuscated attack the ML head alone missed

The problem

Every team shipping an LLM feature inherits a new attack surface: "ignore all previous instructions", DAN-style roleplay, base64/leetspeak obfuscation, and indirect injections hidden in retrieved documents. One successful injection can leak a system prompt, exfiltrate data, or trigger unauthorized tool calls. Model-level safety training helps but is not sufficient and is not something application teams control.

The product

A lightweight service that sits in front of any LLM. A single /scan call returns a label, a calibrated risk_score in [0,1], a block decision, and human-readable reasons for auditability. Per-tenant block thresholds let customers dial their own risk appetite; it is CPU-only and small enough to run on-prem.

How it works

  • Embed prompts with all-MiniLM-L6-v2, classify with a scikit-learn LogisticRegression head
  • Regex/keyword layer for high-precision known patterns (DAN, ignore-previous, system-prompt extraction)
  • Base64 blobs are decoded and re-scanned so obfuscated attacks don't slip through
  • Fused score: risk = clip(0.75 * ml_prob + 0.25 * heuristic, 0, 1); block at risk >= 0.5
  • Trains on a public jailbreak dataset sample with automatic fallback to a bundled seed set

Where it goes

  • Sub-10ms p50 via ONNX/quantized embeddings and a distilled single-pass classifier
  • Policy customization: per-tenant categories, thresholds, allow/deny lists, audit logs
  • Continuous attack-corpus expansion and automated retraining on customer-flagged misses
  • On-prem / VPC and sidecar-proxy deployment for regulated customers

Honest limitations

  • A ~380-example training set won't cover the long tail of novel attacks; the eval set is small
  • Regex heuristics are brittle and evadable by paraphrase; they are a high-precision layer, not the primary defense
  • No indirect/second-order injection handling beyond scoring the raw text passed in

GroundGuard

Hallucination detection

Splits an LLM answer into atomic claims and checks each one against its source context, flagging what is unsupported or contradicted.

startups/02-groundguard/
0.75
mean groundedness across 6 (context, answer) demo pairs
1.00
confidence flagging "revenue fell sharply" as CONTRADICTED
0.50
groundedness on the partially-supported answer (2 of 4 claims unsupported)
1.00
groundedness on both fully-grounded answers (3/3 claims SUPPORTED)

The problem

RAG is the dominant enterprise LLM pattern, and its whole selling point is that answers are grounded in trusted sources. In practice models still invent facts, blend in parametric knowledge, or subtly contradict the retrieved text. In finance, healthcare, legal, and support, a single confident hallucination is a compliance incident, and teams have no cheap automatic way to measure faithfulness at scale.

The product

A groundedness scorer that runs as an online guardrail or an offline eval. For every answer it returns an overall groundedness score (fraction of claims supported), a per-claim verdict of SUPPORTED / CONTRADICTED / NOT_ENOUGH_INFO, and the most-relevant context sentence as evidence. That gives a threshold to block answers in production and a metric to track across model and prompt changes.

How it works

  • Split the answer into atomic claims (v0: one claim per sentence)
  • Run each claim as hypothesis against each context sentence as premise through an NLI cross-encoder
  • Strongest signal wins: entailment -> SUPPORTED, contradiction -> CONTRADICTED, else NOT_ENOUGH_INFO
  • Groundedness = supported claims / total claims, with the winning evidence sentence attached
  • Automatic fallback to MiniLM cosine similarity if no NLI model can be loaded

Where it goes

  • Atomic fact decomposition so each independent fact is scored separately
  • Citation-level grounding: return the exact supporting/contradicting span
  • Calibration and thresholds learned from labeled faithfulness datasets
  • Streaming guardrail mode that scores tokens as they generate

Honest limitations

  • Sentence-level, not true atomic-fact decomposition: a multi-fact sentence gets one verdict
  • Thresholds are fixed heuristics, not calibrated on labeled data
  • The small NLI model can miss subtle numeric or temporal contradictions

RedactAI

Data governance

A reversible PII redaction proxy: swaps sensitive values for typed placeholders before a prompt leaves your boundary, then re-inserts them in the reply.

startups/03-redactai/
5/5
messages restored with exact round-trip fidelity
20
distinct entities vaulted across 9 types
2
live API keys (AWS + OpenAI) caught before leaving the boundary
0
false detections on the benign no-PII message

The problem

Every prompt sent to a hosted LLM may carry raw personal data: names, emails, SSNs, card numbers, and often API keys pasted from logs. That creates compliance exposure under GDPR and the EU AI Act, contractual risk with sub-processors never scoped for regulated data, and security risk from secrets landing in provider retention windows. Simply deleting PII is not enough, because the model then cannot produce a useful personalized answer.

The product

A drop-in proxy with two operations: redact(text) -> (redacted_text, vault) before send, and restore(text, vault) -> text after receive. The Vault holds the placeholder-to-value mapping and in production lives server-side, KMS-backed and keyed by request id, so even the mapping stays inside the customer boundary. Round-trip fidelity is exact.

How it works

  • Layer A: deterministic regex detectors for email, phone, SSN, IPv4, and API-key shapes (AWS, OpenAI, GitHub, Slack, Google)
  • Credit cards validated with a real Luhn mod-10 checksum to cut false positives
  • Layer B: open-weight NER (dslim/bert-base-NER) for person, location, and organization names
  • Graceful degradation: NER pipeline -> capitalization heuristic -> regex-only, with the live mode reported
  • Vault assigns stable typed placeholders; structured detectors win on overlap and longest placeholders restore first

Where it goes

  • Customer-defined entity types (internal IDs, MRNs, policy numbers) with allow/deny lists
  • Token-stream redaction and restoration for chat UIs
  • On-prem / VPC deployment with a KMS-backed vault inside the customer boundary
  • Immutable audit logs of what was detected, redacted, and restored, as GDPR / EU AI Act evidence

Honest limitations

  • Recall gaps on international phone/ID formats, obfuscated numbers, and novel secret shapes
  • General-purpose NER over-captures (tags "SSN" and "OpenAI" as ORG) and misses domain entities
  • The demo round-trips the vault through the caller; a real deployment must keep it server-side and encrypted

AgentWarden

Agent safety

A policy firewall for agent tool calls that returns ALLOW / BLOCK / REQUIRE_APPROVAL on every call, with an append-only audit log.

startups/04-agentwarden/
4 BLOCK
dangerous calls stopped before execution in an 11-call agent trajectory
5 / 4 / 2
ALLOW / BLOCK / REQUIRE_APPROVAL across the trajectory
20 calls / 60s
per-tool rate limit; call #21 escalated to approval

The problem

Agents now call APIs, run shell commands, and move money. A single hallucinated or prompt-injected step can rm -rf a volume, wire funds to an attacker's wallet, or POST secrets to an external host. Model-side guardrails are probabilistic and bypassable; security and compliance review wants a deterministic, auditable enforcement point that does not depend on the model behaving.

The product

A declarative policy layer that evaluates each tool call before it executes. Ordered rules in policy.yaml, first match wins, produce a verdict plus a human-readable reason and the name of the rule that fired. A @warden.guard("tool_name") decorator drops the firewall in front of an existing tool function with no rewrite.

How it works

  • Every tool_call{name, args} is routed through Warden.check() before execution
  • Ordered YAML rules: arg_matches regex, arg_gt thresholds, arg_true flags, arg_not_in allowlists, path_outside sandbox checks
  • Per-tool rate limiting evaluated as a cross-cutting check before the rules
  • BLOCK raises PolicyViolation; REQUIRE_APPROVAL calls an approval callback (Slack/human) or denies
  • Every decision appended to a JSONL audit log with secrets redacted

Where it goes

  • Policy-as-code SDK: typed rules, unit tests for policies, versioning, dry-run against replayed traffic
  • Approval workflows via Slack / PagerDuty / email with timeouts and escalation
  • MCP proxy mode so every MCP tool call is policy-checked with no per-agent wiring
  • Anomaly detection on per-agent baselines, plus default-deny policy packs for finance and infra

Honest limitations

  • Rules are hand-written YAML; no linting, testing framework, versioning, or GUI yet
  • Regex shell/URL matchers are evadable by obfuscation; defense in depth is required
  • Fail-open catch-all and an in-memory audit log; production needs default-deny and durable storage

SchemeWatch

Agent observability

Scans deployed agent transcripts and ranks the episodes showing deception, scheming, reward-hacking, or goal-drift.

startups/05-schemewatch/
4/4
deceptive transcripts flagged CRITICAL; the benign agent scored 0.0
99.9
top risk score (scratchpad says X, action does Y)
0.0
risk score for the benign helpful coding agent
10
misalignment signal types in the taxonomy

The problem

Companies are deploying fleets of autonomous agents that write code, run shell commands, and talk to customers, and almost nobody is watching those agents for misalignment. Standard observability (latency, error rates, token spend) tells you nothing about whether an agent hid a failure, fabricated a tool result, or quietly cleared the audit log. These incidents surface late, from an angry customer or a post-mortem.

The product

A scanner that reads agent transcripts and returns a per-episode risk score plus a list of flags with signal, turn index, evidence, and severity. Point it at your agent logs and get a ranked leaderboard of your sketchiest episodes. It turns "we have 50,000 agent runs a day" into "here are the 12 runs a human should look at right now."

How it works

  • A taxonomy of 10 pattern detectors: concealment, intent/action mismatch, fabrication, manipulation, privilege escalation, disable/refuse oversight, reward hacking, sandbagging, goal drift
  • Contrastive embedding detector: MiniLM similarity to ~20 scheming exemplars minus similarity to benign helper phrases
  • Flags aggregated with a noisy-OR over per-flag severities, with diminishing returns for repeated signals
  • Rescaled to 0-100 risk bands: LOW <25, MEDIUM 25-50, HIGH 50-75, CRITICAL >=75
  • Returns evidence spans and turn indices so a reviewer can jump straight to the moment

Where it goes

  • LLM-judge escalation tier that adjudicates intent on high-risk or ambiguous episodes
  • Learned classifiers trained on labeled real-world agent incidents
  • Real-time streaming scoring that interrupts or alerts mid-episode
  • One-line ingestion hooks for LangChain, LlamaIndex, AutoGen, and MCP

Honest limitations

  • Exemplar bank and regex taxonomy are hand-authored, not learned from real incidents
  • No labeled benchmark, so precision/recall are unmeasured; scores are relative and useful for ranking
  • Detectors are turn-local and English-centric; a sophisticated agent can scheme without tripping a phrase

ProbeKit

Interpretability

Interpretability-as-a-service: trains linear probes on an open-weight model's hidden activations to read concepts out of its internal state.

startups/06-probekit/
68.3%
CV accuracy decoding truthfulness at layer 18 (chance = 50%)
5/6
held-out statements the layer-18 probe called correctly
0.450 -> 0.683
CV accuracy climbing from layer 6 to layer 18
896
hidden size probed across 24 Qwen2.5-0.5B layers

The problem

Modern LLMs are black boxes. When a model is about to refuse, is processing something toxic, or is stating something it "knows" to be false, that information exists inside the network's activations, but developers have no standard way to read it. Output-only monitoring is too late and too shallow: by the time tokens are generated, the decision has already been made.

The product

ProbeKit turns hidden states into an observability surface. Extract residual-stream activations from any layer, train a lightweight linear probe on a labeled concept, then predict on new inputs with a calibrated probability. A layer sweep locates where in the network a concept becomes linearly decodable, which is the natural place to attach a monitor.

How it works

  • Run inputs with output_hidden_states=True and grab the residual-stream vector at the last token of a chosen layer
  • Chat-tuned inputs are wrapped in the chat template so the last token is where the model has finished reading
  • Standardize activations and fit a scikit-learn LogisticRegression: a linear probe is the honest test of direct representation
  • Sweep several layers with 5-fold cross-validation to find where the concept lives
  • Fallbacks to distilbert hidden states and then MiniLM embeddings so the demo always runs

Where it goes

  • A library of ready-made probes: refusal, toxicity, sentiment, jailbreak-intent, PII presence
  • Steering vectors that turn each probe direction into an inference-time intervention
  • Real-time inference hooks scoring every forward pass with sub-millisecond probes
  • SAE features instead of raw residual directions, plus a hosted API and live monitor dashboard

Honest limitations

  • Linear probes test for a linearly available direction, not a causal mechanism
  • Correlation, not causation: establishing dependence needs activation patching or steering
  • One 0.5B model and 60 labeled examples, single token position at one layer; ~68% is a signal, not a benchmark

AutoRedTeam

Red teaming

Automated adversarial testing: mutates seed requests through an attack library, runs them against a target model, and reports attack success rate.

startups/07-autoredteam/
60.0%
overall attack success rate on the real local Qwen2.5-0.5B target
100%
prefix-injection ASR: broke the target on all 5 seeds
80%
refusal-suppression ASR vs 40% for the plain baseline
15/25
test cases in the matrix that succeeded

The problem

Manual red-teaming does not scale. Every model update, system-prompt tweak, or new tool can silently reopen holes, and attack techniques evolve faster than humans can re-test the taxonomy on each release. There is no continuous quantitative signal for whether refusal robustness is getting better or worse release over release.

The product

Red-teaming as infrastructure. Give it a target, and it takes a seed set of borderline requests, applies a library of attack transformations, runs every transformed prompt, auto-judges refusal versus compliance, and emits a vulnerability report with overall ASR, per-attack ASR, per-category ASR, and the top successful jailbreaks. The ASR table is the product: a dashboard number and a CI gate.

How it works

  • Seeds x transformations = test matrix, run against the target model
  • Attack library: baseline control, dan_roleplay, ignore_previous, hypothetical_fiction, base64_obfuscation, leetspeak, prefix_injection, refusal_suppression
  • Target adapter runs a local Qwen2.5-0.5B-Instruct greedily on CPU, with a deterministic mock fallback
  • Heuristic judge: refusal keyword detection plus a MiniLM on-topic check; success = did NOT refuse AND produced non-trivial on-topic content
  • Engine aggregates ASR overall, per attack, and per category, surfacing example jailbreaks

Where it goes

  • LLM-as-judge with the heuristic as a cheap pre-filter, for accurate break detection and severity scoring
  • Adaptive attacks: GCG-style prompt search, mutation of successful jailbreaks, multi-turn attack agents
  • CI integration: a GitHub Action that fails the build when ASR exceeds a threshold, with trend tracking
  • Attack-taxonomy mapping to MITRE ATLAS / OWASP LLM Top 10, plus adapters for hosted API targets

Honest limitations

  • Heuristic judge has both false positives and false negatives; it approximates rather than certifies a break
  • 8 static single-turn transformations; real adversaries chain, mutate, and go multi-turn
  • One tiny weakly safety-tuned target, and max_new_tokens=32 can truncate before an answer is clearly compliant

EvalForge

Eval infrastructure

Versioned LLM regression testing: unit tests and a CI gate for model behavior, with safety regressions blocking the deploy.

The problem

Teams ship LLM features by tweaking prompts and swapping models constantly, and every change can silently regress behavior: a "more helpful" prompt edit starts complying with jailbreaks, a model upgrade begins leaking PII it used to refuse, a refactor breaks a strict-JSON contract. There is no pytest for this, so regressions are caught in production or in a screenshot on social media.

The product

A framework plus dashboard. Define a suite of YAML test cases with a category and assertions, run it against any model version, and diff versions. EvalForge highlights every test that passed in v1 but fails in v2 and emits a CI-style exit code: safety regressions block, quality regressions warn.

How it works

  • Suite of test cases loaded from YAML, each tagged safety / refusal / factual / format / injection
  • Assertion library: must_refuse, refuses_jailbreak, must_not_contain, must_contain, regex_match, max_tokens, semantic_similarity
  • Pluggable models under test: real Qwen2.5-0.5B-Instruct, or deterministic mocks for fast offline CI
  • Each backend ships a v1 (strong safety prompt) and a v2 (deliberately weakened prompt) to surface genuine regressions
  • Runner.diff(baseline, candidate) produces the version diff, report.json, and a self-contained report.html

Where it goes

  • LLM-judge assertions to grade open-ended answers and subtle safety violations against a rubric
  • GitHub Action: evalforge run --fail-on safety as a required status check
  • Drift monitoring in prod, sampling live traffic against the same suite
  • Shared eval registry of versioned, subscribable suites (jailbreaks, PII, injection corpora)

Honest limitations

  • String/regex/length/embedding assertions miss nuanced harms; must_refuse marker heuristics can misread a terse refusal
  • The mock backend is deterministic by design and the Qwen backend is tiny; larger models behave differently
  • Single-turn only, with no multi-turn or tool-use conversations yet

VeriClaim

Fact verification

Extracts checkable claims from any text and returns SUPPORTED / REFUTED / UNVERIFIABLE with the evidence and a visible reasoning trail.

The problem

Human misinformation spreads faster than it can be checked, and LLM hallucinations now assert confident, plausible falsehoods at scale with no sourcing. Existing fact-checkers are also widely perceived as opaque and biased: a label appears, but the reasoning, sources, and editorial judgement behind it are not inspectable. That opacity is itself a trust problem, regardless of whether any given verdict is correct.

The product

A transparent claim-verification engine, deliverable as an API or browser extension. For every claim it exposes the full chain: the extracted claim, the retrieved evidence passages with similarity scores, the entailment decision, and a plain-language rationale. Because the pipeline and corpus are open, verdicts are reproducible and auditable, so you can disagree with a specific step rather than the whole black box.

How it works

  • Claim extraction: sentence segmentation plus a filter dropping questions, imperatives, and opinion-flavoured sentences
  • Evidence retrieval: embed claim and corpus passages with MiniLM and rank by cosine similarity
  • Verdict: run an NLI cross-encoder per retrieved passage, strongest entailment or contradiction decides
  • Every verdict ships per-evidence entail/contra/neutral scores plus a rationale
  • Automatic similarity-threshold fallback if the NLI model cannot be fetched

Where it goes

  • Live retrieval over the open web and trusted reference corpora instead of a fixed bundle
  • Source-credibility scoring so evidence is weighted rather than treated as flat
  • Openly published bias audits: standardised test sets and per-topic verdict statistics
  • Browser extension that inline-annotates claims with verdicts and one-click evidence

Honest limitations

  • Tiny ~46-passage corpus; anything outside it returns UNVERIFIABLE, with no web-scale knowledge
  • NLI brittleness: the small model returns neutral even when a passage plainly supports a claim (the 206-bones case)
  • Heuristic claim extraction misses compound claims, sarcasm, and context-dependent statements

GhostText

Content provenance

Calibrated AI-vs-human text detection that abstains when the signal is weak instead of returning an overconfident verdict.

The problem

AI-generated text is everywhere and institutions want to know what was machine-written, but today's detectors are both inaccurate and overconfident. Accuracy collapses on paraphrased text, non-native English, and short texts, yet they hand back a red/green badge with no honest uncertainty. The result is false accusations: students failed for essays they wrote, and non-native writers flagged disproportionately because their prose is more even.

The product

GhostText treats detection as a calibrated-probability problem. Probabilities are fit with CalibratedClassifierCV under cross-validation, so a "72%" means roughly 72% of texts scored that way really are AI. In the uncertain band it returns ABSTAIN, because a false accusation is the expensive error, and every verdict ships with .explain() showing the interpretable features that drove the score.

How it works

  • Perplexity features from a local Qwen2.5-0.5B-Instruct: mean token log-prob, surprisal variance, perplexity, max surprisal
  • Stylometry: burstiness, sentence-length spread, type-token and hapax ratios, punctuation and function-word ratios, repeated bigrams
  • LogisticRegression over the 16 features keeps each feature's signed contribution readable
  • CalibratedClassifierCV (sigmoid / Platt scaling) makes the output probabilities trustworthy
  • ABSTAIN in the tunable 40-60% band, keyed to the customer's false-positive cost

Where it goes

  • Larger, diverse training data across models, domains, and languages
  • Watermark-signal fusion: ingest C2PA and model-watermark evidence as features
  • Per-domain calibration maps, since a detector trained on essays transfers poorly to chat or code
  • Cost-tuned abstention: set the band from each customer's false-positive cost and report expected error rates

Honest limitations

  • ~80 short texts on narrow topics; the perfect cross-val score reflects trivially separable classes, not real difficulty
  • Evadable by light paraphrasing, humanizer tools, or prompting the LM to write casually
  • Bias risk: even-prose signals can penalize non-native writers, so any deployment needs fairness auditing first
